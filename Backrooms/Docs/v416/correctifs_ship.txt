## Defauts et risques traites

D1. REJOUER : une note lue en rejeu disparaissait du carnet de la partie (defaut trouve dans le code, regle documentee ;
    pas encore reproduit dans Unreal).
    Cause : ABRPlayerController::WriteActiveSave, branche du rejeu (BRStory::WritePolicyFor : bJournalUnion), ne completait
    que les entites du journal (UBRSaveGame::Discovered) ; les documents lus (ABRCharacter::ReadNotes -> UBRSaveGame::Notes)
    n'etaient jamais ecrits. GAMEPLAY_v4.14 § 1 et RAPPORT_v4.14 § 2.1 : "un document ou une entite decouverts en rejeu
    restent au carnet (union, rien n'est retire)" ; prompt v4.16 § 10 : "hors union explicite des documents".
    Avant : note lue en REJOUER, retour a la campagne (CONTINUER, ou relance du jeu) : la note n'est plus dans le carnet.
    Apres : la note s'ajoute aux notes de la partie (union, jamais de retrait, aucune autre ecriture). Le rejeu n'ecrit
    toujours rien d'autre (equipement, sante, morts, temps, niveau, session, campagne, histoire, parcours).
    Tests : -BRAutoTestV416Ship, etapes "v4.16 rejeu : consommation, degats, document, entite, ecritures" (fichier relu : note
    et entite ajoutees, champs durables identiques ; sur l'ancien code : PROBLEME, la note manque), "v4.16 rejeu : mort",
    "v4.16 rejeu : fermeture du jeu", "v4.16 campagne : session reprise" (la note au carnet apres CONTINUER), "v4.16
    migration : REJOUER, note lue, fermeture" (format 5 : seule l'union est ecrite, copie _Format5 intacte) ; banc de
    l'histoire, section I (le modele du banc distingue maintenant entites et documents ; ligne "v4.16 : le document lu en
    rejeu complete les notes de la partie" ; 95 verifications, 94 avant).

D2. Paquet Shipping : tous les plans de test etaient joignables depuis la ligne de commande d'un joueur (risque trouve dans
    le code). Cause : ABRAutoTest::IsRequested ne distinguait pas la version publiee ; -BRAutoTestStay gardait le jeu ouvert
    a la fin d'un plan, avec l'etat du test (ex. -BRAutoTest -BRAutoTestV415 -BRAutoTestStay : partie ouverte avec le
    personnage invincible du test) ; -BRNetTest y lancait aussi son plan (dont les barrieres ne marchent pas en Shipping).
    Apres : en Shipping, seuls -BRAutoTest -BRSmokeTest (demarrage) et -BRAutoTest -BRAutoTestChapter (traversee) sont
    acceptes ; -BRAutoTestStay est ignore (le jeu se ferme toujours a la fin) ; pas de test reseau. Les commandes de la
    console restent fermees (AreCheatsAllowed, inchange). Hors Shipping : rien ne change.
    Test : check_package.py --launch --chapter sur le paquet (les deux essais acceptes passent) ; compilation de la cible
    Shipping (branches UE_BUILD_SHIPPING). Le refus des autres plans n'est pas essaye en jeu (il faudrait lancer le paquet
    avec un plan refuse : a faire a la main, attendu : menu ordinaire, aucun rapport dans Saved/AutoTest).

D3. Traversee du chapitre : les parties du joueur auraient ete lues au lancement (risque trouve dans le code). Cause : la
    liste du menu (ABRPlayerController::BeginPlay -> RefreshSaves -> BRSaves::Load) lit les emplacements avant la premiere
    etape d'un test ; BRSaves::Load peut reprendre une copie de secours ou mettre un fichier illisible de cote. Apres :
    avec -BRAutoTest -BRAutoTestChapter, BRSaves commence avec le prefixe de test (BR_AutoTestChapitre_) : les parties du
    joueur (BR_Partie_*) ne sont ni lues ni ecrites. Test : -BRAutoTestChapter, premiere note "parties de test ... des le
    lancement oui" (PROBLEME sinon).

N1. Nouveau : traversee du premier chapitre publie dans le paquet (Source/Backrooms/Private/BRAutoTestV416Ship.cpp,
    -BRAutoTestChapter) et son controle (Tools/Build/check_package.py --chapter, Tools/Build/build_windows.ps1 -Chapter).
    - parties de test (prefixe BR_AutoTestChapitre_, pose des le lancement), canal publie (compile dans le paquet, impose
      hors Shipping), parcours lineaire ;
    - NOUVELLE PARTIE par le vrai menu (SOLO, VOS PARTIES, NOUVELLE PARTIE, COMMENCER) ; ou -BRChapterSeed=<graine du
      parcours> [-BRChapterIntro=<graine du Level 0>] (le rapport les donne) pour rejouer une disposition ;
    - Level 0 : marche jusqu'a la porte de service, touche d'interaction ; Niveaux 1, 37 et 2 : missions resolues en
      marchant, sorties prises a pied (les marches de BRAutoTestV412.cpp et BRAutoTestV413.cpp, entrees du joueur seules) ;
      fin du chapitre ;
    - a chaque arrivee, la partie relue du disque (etape accomplie, reprise, niveau explore, session et graine du niveau,
      parcours, morts) ; Poolrooms resolues : fermeture (ecriture de QUITTER) puis reprise par VOS PARTIES et CONTINUER
      (meme graine, meme etat de mission, sortie ouverte) ; fin du chapitre ecrite par le jeu lui-meme (fichier relu sans
      ecriture du test) ; apres un redemarrage : carte de la partie, CONTINUER au Niveau 2, mission accomplie ; nettoyage ;
    - -BRChapterPhase=1|2|3 : trois lancements separes par de vraies fermetures du jeu (l'ecriture de la fermeture est celle
      du jeu, ABRPlayerController::EndPlay) ; 0 (defaut) : un lancement. Etat d'une phase a l'autre :
      Saved/SaveGames/BR_AutoTestChapitre_Etat.txt (efface au nettoyage) ; etat de chaque phase : Chapitre.json (dossier du
      rapport) et -BRChapterOut=<fichier> ;
    - une etape qui n'a pas pu se faire (niveau non atteint, entite seule sur le passage, phase precedente incomplete) est
      NON VERIFIEE et la suite de la traversee est sautee d'un bloc (etapes de garde), jamais comptee comme reussie.
    check_package.py --chapter : --chapter-mode restart (defaut, trois lancements) ou single ; chaque phase jugee comme le
    test de demarrage (rapport de cet essai, schema, code de sortie) et par son etat (niveaux atteints, fermeture, reprise,
    fin enregistree, apres relance, nettoyage, canal public) ; une phase incomplete arrete la suite (INCOMPLET, code 2) ;
    l'ensemble exige 0 -> 1 -> 37 -> 2 -> fin du chapitre. --require-chapter l'exige. 15 tests ajoutes a
    Tools/Build/tests/test_packaging.py (jeu simule : trois phases, un lancement, apres le demarrage, demarrage en echec,
    phase incomplete qui arrete la suite, phase en echec, etat absent, rapport d'un autre essai, etat d'une autre phase,
    niveaux inattendus, fin non enregistree, reussi mais non valide, canal interne, exige hors hote, non demande).
    build_windows.ps1 : -Launch (test de demarrage), -Chapter (demarrage puis traversee exigee, rapport JSON
    Build/Windows/check_package_Shipping.json), -ChapterOut <dossier> ; -Chapter refuse avant la construction un contenu
    autre que public ou une autre plateforme que Win64.

R1. Ecriture de l'arrivee pendant le fondu (risque trouve dans le code, non corrige ici, sans effet de jeu mesurable) :
    ABRPlayerController::OnLevelLoaded programme l'ecriture 2 s apres le chargement, mais le fondu d'arrivee peut durer
    jusqu'a 1,6 s + 8,5 s (attente des shaders, ABRWorld FadingIn). Pendant le fondu, WriteActiveSave n'ecrit pas la
    session du nouveau niveau (niveau, histoire et decouvertes, si) : la session suivante est ecrite par
    l'enregistrement automatique (60 s) ou par QUITTER. Consequence : un jeu tue dans cette minute reprend le niveau neuf
    (meme graine en parcours lineaire ; rien n'y avait encore ete fait). La traversee relit donc le fichier chaque seconde
    jusqu'a la session du niveau (70 s au plus) et dit combien de temps apres l'arrivee elle l'a trouvee.

R2. -BRNetTest n'est plus accepte par un paquet Shipping (D2) : pour un essai reseau sur deux machines, construire un
    paquet Development (build_windows.ps1 -Config Development) ou lancer l'editeur.
